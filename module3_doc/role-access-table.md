# Storage and Retrieval Role Access Table

Project: proj-lessons

| Role | Storage operations | Retrieval operations | Classification ceiling | Why |
|---|---|---|---|---|
| `planner` | none | `retrieve` | internal | Retrieves permitted prior lessons before proposing an approach -- required responsibility 1. Never writes to storage; its output is a plan, not a record. |
| `implementer` | `write_entry` only | none | n/a for storage (server rejects any `confidential`/`secret` write regardless of caller; `implementer` is instructed to only ever pass `internal`) | Records one new lesson learned when the work surfaces something a future session couldn't reconstruct from the code alone -- required responsibility 2. No `read_entry`/`list_entries`/`update_entry`/`delete_entry` -- it adds a new entry, it does not browse or edit history. No retrieval access -- it is not the role that needs prior context; `planner` already supplied that during planning. |
| Orchestrator (top-level session; stands in for Reviewer/Tester) | none | `retrieve`, called directly (not via a subagent `tools:` grant, since the orchestrator is the top-level session and isn't subject to a `tools:` allowlist) | internal | Retrieves relevant standards or prior lessons while evaluating the implementer's result -- required responsibility 3, standing in for a dedicated Reviewer role not yet implemented as its own subagent (same pattern as the orchestrator's own `./mvnw test` run standing in for Tester). This access is policy-governed (`CLAUDE.md` instructs it) rather than technically restricted -- a materially weaker guarantee than a subagent's `tools:` field, documented explicitly in `CLAUDE.md`'s "Storage and Retrieval Access" section. |
| `reviewer` (designed, not implemented as a runnable agent) | none (planned) | `retrieve` (planned) | internal (planned) | Would retrieve relevant standards while reviewing a diff, fulfilling required responsibility 3 directly once implemented, rather than folded into the orchestrator. |
| `tester` (designed, not implemented as a runnable agent) | none (planned) | none (planned) | n/a | Runs tests and reports pass/fail; has no need for prior-lesson context to do that job. |

## Notes

- Every implemented role also retains its Exercise 3.1 `coursetools` grants (`planner`: `file_read`, `codebase_search`; `implementer`: `file_read`, `file_write`, `codebase_search`). As of the Step 6 verification in this exercise, none of the three `coursetools` file operations can reach anything under `.memory/` at all, regardless of role -- see `lessons-learned-workflow-run.md` for the full finding, fix, and retest. This keeps the storage/retrieval access model in this table as the *only* path into `.memory/` content, closing a gap that would otherwise have let a role's general-purpose file tools bypass the classification and audit guarantees this table describes.
- `classification_ceiling` on `retrieve` is a caller-supplied parameter, not a value the server independently binds to a role's identity. `planner`'s instructions require it to always pass `"internal"`, but this is a policy the agent is expected to follow, not an enforced guarantee in the same sense as `write_entry`'s classification check (which genuinely rejects a `confidential`/`secret` write server-side regardless of what the caller claims). This distinction is documented explicitly in `CLAUDE.md` so it is not mistaken for a stronger guarantee than it is.
